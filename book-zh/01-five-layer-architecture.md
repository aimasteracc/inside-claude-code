# 第 1 章 —— 五层提示词架构

*一个顶级编程智能体的「系统提示词」不是一段字符串。它是一个由许多个带版本号的小单元组成的库，每个单元只干一件事。*

## 为什么重要

大多数人会把智能体的系统提示词想象成一整块英雄主义的文本 —— 几千字的「你是一个乐于助人的助手，写干净的代码」。正是这种心智模型，让大多数自研智能体停滞不前：单体提示词无法做版本管理，无法做 A/B 测试，无法按需选择性加载，而且一旦长到超过一屏就开始腐烂。

Claude Code 的提示词层，其行为表现得就像是按相反方式构建的。可观察到的行为与这样一个系统相吻合：它被拆解成**数十个独立单元**，归入大约**六大类别**，每个单元都带着自己的名称、简短描述和一个版本标签。理解这种拆解，是本书后续一切内容的地基 —— 因为第 II 部分的每一个模式，都是这一个架构决策的衍生结果。

## 六大类别

跨越许多次会话观察这个智能体，你可以推断出一种清晰的关注点分离，分成大约六个提示词单元家族：

| 类别 | 职责 | 一句话记忆 |
|----------|-----|-----------------|
| **系统提示词** | 核心人格 + 行为准则 | 「AI 是谁、该怎么做」 |
| **系统提醒** | 条件触发的事件通知 | 「发生了什么 —— 注意一下」 |
| **工具描述** | 每个工具的认知边界 | 「AI 能用什么、怎么用」 |
| **智能体提示词** | 子智能体的专属人格 | 「每个子智能体的职责」 |
| **数据** | SDK/API 参考知识注入 | 「AI 的参考手册」 |
| **技能** | 针对特定任务的内置能力包 | 「一键触发的能力包」 |

```
许多个小提示词单元 = ~6 类 x 关注点分离
┌─────────────────────────────────────────────────────┐
│  系统提示词     ← 人格 + 规则（「我是谁」）           │
│  系统提醒       ← 事件通知（「注意这个」）            │
│  工具描述       ← 能力边界（「我能做什么」）          │
│  智能体提示词   ← 子智能体人格（「分工协作」）        │
│  数据           ← 知识注入（「参考手册」）            │
│  技能           ← 内置能力（「一键触发」）            │
└─────────────────────────────────────────────────────┘
```

带着工程师的眼光再读一遍那张表。这不是提示词*写作*，而是提示词*架构* —— 与把一个代码库拆分成职责单一的模块，是同一种本能。这样的单元有很多，而单独看每一个都很小 —— 往往只有几十个 token —— 而这恰恰是让它们能被组合、被版本管理、被按需加载的原因。

## 第 1 层：系统提示词 —— 以及「不」的惊人分量

系统提示词层承载着智能体的人格和它的硬性规则。其中最能说明问题的物料是这些**约束** —— 而且数量相当多。每一条都很小，且大多以禁令的形式表述。其中最重要的几条是：

| 约束 | 规则 |
|------|------|
| 不要过度抽象 | 不为一次性操作创建抽象 |
| 不要过度构建 | 不做超出请求范围的改进 |
| 不加兼容垫片 | 彻底删除未用代码；不加垫片 |
| 不给时间估计 | 不承诺工作要花多久 |
| 不做防御性过度处理 | 不为不可能发生的状态加防护 |
| 修改前先读 | 改动代码前先读代码 |
| 尽量少建新文件 | 优先编辑现有文件 |
| 安全基线 | 避免注入、XSS 以及 OWASP 那一整套 |

注意这些表述方式。它们大多被表述为*不*该做的事。这是整套提示词集合中最重要的一个观察，我们会用整个第 3 章来讲它：**一个优秀智能体的大部分指令，定义的是它*绝不能*做什么。**能力是简单的部分 —— 模型本来就想写代码。工程的难点在护栏上。

## 第 2 层：工具描述 —— 能力，就是 AI 能*看见*的东西

模型看不见的工具，等于不存在。工具描述层正是智能体对自身能力绘制*认知地图*的地方。系统提示词甚至会让智能体倾向于使用专用工具，而非裸的 shell：

| 操作 | 专用工具 | 不使用 |
|-----------|----------------|-----|
| 读文件 | Read | cat/head/tail/sed |
| 编辑文件 | Edit | sed/awk |
| 创建文件 | Write | echo / heredoc |
| 查找文件 | Glob | find/ls |
| 搜索内容 | Grep | grep/rg |

而风险最高的工具，得到的围堵也最多。在所有工具里，裸的 shell 背着的专用约束远比其他工具密集 —— 许多条各不相同的规则，聚成几个系列：

| 约束系列 | 关键规则 |
|-------------------|-----------|
| 沙箱 | 默认沙箱；基于证据放行；重试策略 |
| Sleep | 等待要短；绝不轮询；优先用一次检查 |
| Git | 不跳过 hook；不强制推送；优先新建提交 |
| 路径/命令 | 绝对路径；为空格加引号；用 `&&` 串联 |

这条原则可以推广：**工具越强大，围在它周围的围堵网就越密。**每一条规则读起来都像是能追溯到一次真实事故 —— 否则它根本不会挣到一个属于自己的带版本号的条目。

## 第 3 层：系统提醒 —— 感知，而非指令

系统提醒是智能体的*中断处理程序*。它们并非常驻开启；它们在满足条件时才触发：

| 类别 | 示例 | 触发时机 |
|-------|----------|-----------|
| 文件系统 | 文件被修改、被截断，或现已为空 | IDE 或外部的编辑 |
| 计划模式 | 规划已激活；已退出规划 | 进入/离开规划 |
| Hook | 某个 hook 成功了；某个 hook 拦截了一个动作 | 某个 hook 返回时 |
| 安全 | 读取一个文件之后的安全检查 | 读取一个文件之后 |
| 会话 | token 用量；预算花费 | 会话状态发生变化时 |

这就是事件驱动的提示词：上下文在*相关时*才被注入，而不是被永久塞进去。这正是智能体如何在不为每一轮都付出「描述整个世界」的 token 成本的前提下，保持对一个不断变化的世界的感知。

## 第 4–6 层：委派、知识与技能

- **智能体提示词**为每个子智能体赋予各自的人格。其中分量最重的是一个安全监视者 —— 一个为自主运行而设的专职监视器，明显比其余的都要大。其他还包括一个验证专家（构建 + 测试 + 检查），以及一些在会话之间整合记忆的后台例程。
- **数据**注入参考知识 —— 跨 Python、TypeScript、Java、Go、C# 等语言的 Claude API 示例 —— 按需加载，而不是常驻在上下文里（这就是我们会在第 4 章重新讨论的「静态 RAG」思路）。
- **技能**是一键触发的能力包；其中最重的一个 —— 一份构建 LLM 驱动应用的指南 —— 属于整个系统中最大的单个提示词单元之列。

## 从来源到理论

观察还讲清楚了一件事 —— 存在一条从产品行为通往可传授理论的路径，分三步走：

```
产品行为              ← 智能体实际运行时的样子
    │ 观察并提炼为 ↓
一个结构化的提示词模型  ← 许多个小单元，已整理、有版本意识
    │ 解读为 ↓
五层理论              ← 解释它「为什么」奏效的框架
```

这里的教训是：最懂这套系统的人，不会停在一篇博客文章。他们贴近地观察行为，提炼出它的一个结构化模型，*然后*才建立起一套理论。这本书把那份工作的成果直接交到你手上。

## 拿去用

要移植的是架构，而不只是那些规则：

- **把你的系统提示词拆成多个文件**，每个文件一个职责。哪怕只是三个文件（`persona.md`、`constraints.md`、`tools.md`），也胜过一个单体。你立刻就获得了版本管理、差异对比和选择性加载。
- **以约束开头。**在写你的智能体*做什么*之前，先写下它绝不能做的那 8–10 件事 —— 用 `不要做 X。因为 Y。除非 Z。` 的句式（即第 3 章里的那个模板）。
- **给每一条规则打版本。**一条规则诞生的当天，就给它加上日期或版本标签。那个标签就是你的事故日志：半年之后，版本之间的差异*就是*你的智能体积累下来的智慧。
- **让上下文变成事件驱动的。**任何你现在每一轮都前置注入的东西 —— 问问自己，它能不能改成只在其触发条件出现时才注入。你的 token 账单和你的信噪比都会因此改善。
- **把你最危险的工具围得最紧。**无论你的「Bash」是什么 —— 一个 shell、一次数据库写入、一笔支付调用 —— 都给它配上你整个栈里最密、最具体的护栏。

**别再写一段提示词了。开始架构一套提示词系统吧 —— 模块化、有版本，并且大部分由「不」构成。**
