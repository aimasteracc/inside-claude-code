# 第 1 章 —— 五层提示词架构

*一个顶级编程代理的「系统提示词」不是一段字符串。它是一个由 110+ 个带版本号的文件组成的文件系统，每个文件只干一件事。*

## 为什么重要

大多数人会把代理的系统提示词想象成一整块英雄主义的文本 —— 几千字的「你是一个乐于助人的助手，写干净的代码」。正是这种心智模型，让大多数自研代理停滞不前：单体提示词无法做版本管理，无法做 A/B 测试，无法按需选择性加载，而且一旦长到超过一屏就开始腐烂。

Claude Code 的提示词层是反过来构建的。它被拆解成 **110+ 个独立文件**，归入**六大类别**，每个文件都带着自己的 `name`、`description` 和 `ccVersion`。理解这种拆解，是本书后续一切内容的地基 —— 因为第 II 部分的每一个模式，都是这一个架构决策的衍生结果。

## 六大类别

对这套提示词集合的逆向工程（追踪到发布版本 `v2.1.97`）揭示出一种清晰的关注点分离：

| 类别 | 数量 | 前缀 | 职责 | 一句话记忆 |
|----------|-------|--------|-----|-----------------|
| **系统提示词** | 67+ | `system-prompt-` | 核心人格 + 行为准则 | 「AI 是谁、该怎么做」 |
| **系统提醒** | 37+ | `system-reminder-` | 条件触发的事件通知 | 「发生了什么 —— 注意一下」 |
| **工具描述** | 73+ | `tool-description-` | 每个工具的认知边界 | 「AI 能用什么、怎么用」 |
| **代理提示词** | 32+ | `agent-prompt-` | 子代理的专属人格 | 「每个子代理的职责」 |
| **数据** | 25+ | `data-` | SDK/API 参考知识注入 | 「AI 的参考手册」 |
| **技能** | 16+ | `skill-` | 针对特定任务的内置能力包 | 「一键触发的能力包」 |

```
110+ 个提示词文件 = 6 类 x 关注点分离
┌─────────────────────────────────────────────────────┐
│  系统提示词 (67)  ← 人格 + 规则（「我是谁」）         │
│  系统提醒 (37)    ← 事件通知（「注意这个」）          │
│  工具描述 (73)    ← 能力边界（「我能做什么」）        │
│  代理提示词 (32)  ← 子代理人格（「分工协作」）        │
│  数据 (25)        ← 知识注入（「参考手册」）          │
│  技能 (16)        ← 内置能力（「一键触发」）          │
└─────────────────────────────────────────────────────┘
```

带着工程师的眼光再读一遍那张表。这不是提示词**写作**，而是提示词**架构** —— 与把一个代码库拆分成职责单一的模块，是同一种本能。

## 第 1 层：系统提示词 —— 以及「不」的惊人分量

系统提示词层承载着代理的人格和它的硬性规则。其中最能说明问题的物料是这些**约束** —— 而且数量相当多。下面是其中最重要的八条，附带它们实际的 token 成本：

| 文件 | Token | 规则 |
|------|--------|------|
| `no-premature-abstractions` | 72 | 不为一次性操作创建抽象 |
| `no-unnecessary-additions` | 78 | 不做超出请求范围的改进 |
| `no-compatibility-hacks` | 52 | 彻底删除未用代码；不加兼容垫片 |
| `no-time-estimates` | 47 | 不给时间估计 |
| `no-unnecessary-error-handling` | 64 | 不为不可能发生的状态加防护 |
| `read-before-modifying` | 46 | 修改前先读代码 |
| `minimize-file-creation` | 47 | 优先编辑现有文件 |
| `security` | 67 | 避免注入、XSS 以及 OWASP 那一整套 |

注意这些命名。八个里有六个以 `no-` 开头。这是整套提示词集合中最重要的一个观察，我们会用整个第 3 章来讲它：**一个优秀代理的大部分指令，定义的是它*绝不能*做什么。**能力是简单的部分 —— 模型本来就想写代码。工程的难点在护栏上。

## 第 2 层：工具描述 —— 能力，就是 AI 能*看见*的东西

模型看不见的工具，等于不存在。工具描述层 —— 73+ 个文件 —— 正是代理对自身能力绘制*认知地图*的地方。系统提示词甚至会让代理倾向于使用专用工具，而非裸的 shell：

| 操作 | 专用工具 | 不使用 |
|-----------|----------------|-----|
| 读文件 | Read | cat/head/tail/sed |
| 编辑文件 | Edit | sed/awk |
| 创建文件 | Write | echo / heredoc |
| 查找文件 | Glob | find/ls |
| 搜索内容 | Grep | grep/rg |

而风险最高的工具，得到的围堵也最多。**单是 Bash 一个工具就背着 30+ 个专门的约束文件**：

| 约束系列 | 条数 | 关键规则 |
|-------------------|-------|-----------|
| 沙箱 | 12 | 默认沙箱；基于证据放行；重试策略 |
| Sleep | 4 | 控制在 1–5 秒；绝不轮询；优先用一次检查 |
| Git | 4 | 不跳过 hook；不强制推送；优先新建提交 |
| 路径/命令 | 10+ | 绝对路径；为空格加引号；用 `&&` 串联 |

这条原则可以推广：**工具越强大，围在它周围的围堵网就越密。**每一条规则都能追溯到一次真实事故 —— 否则它根本不会挣到一个版本号。

## 第 3 层：系统提醒 —— 感知，而非指令

37+ 个系统提醒是代理的*中断处理程序*。它们并非常驻开启；它们在满足条件时才触发：

| 类别 | 示例 | 触发时机 |
|-------|----------|-----------|
| 文件系统 | `file-modified`、`file-truncated`、`file-exists-but-empty` | IDE 或外部的编辑 |
| 计划模式 | `plan-mode-is-active`、`exited-plan-mode` | 进入/离开规划 |
| Hook | `hook-success`、`hook-blocking-error` | 某个 hook 返回时 |
| 安全 | `malware-analysis-after-read` | 读取一个文件之后 |
| 会话 | `token-usage`、`usd-budget` | 会话状态发生变化时 |

这就是事件驱动的提示词：上下文在*相关时*才被注入，而不是被永久塞进去。这正是代理如何在不为每一轮都付出「描述整个世界」的 token 成本的前提下，保持对一个不断变化的世界的感知。

## 第 4–6 层：委派、知识与技能

- **代理提示词（32+）**为每个子代理赋予各自的人格。其中最大的是 `security-monitor`，约 6,426 token —— 一个为自主运行而设的专职监视者。其他还包括一个 `verification-specialist`（构建 + 测试 + 检查），以及一些命名为 `dream-memory-consolidation` 之类的记忆例程。
- **数据（25+）**注入参考知识 —— 跨 Python、TypeScript、Java、Go、C# 等语言的 Claude API 示例 —— 按需加载，而不是常驻在上下文里（这就是我们会在第 4 章重新讨论的「静态 RAG」思路）。
- **技能（16+）**是一键触发的能力包；其中最大的 `build-llm-powered-apps` 约 7,556 token。

## 三层来源体系

逆向工程还讲清楚了一件事 —— 自底向上共有三层物料：

```
cc-source/src/              ← 产品源码（提示词被硬编码在这里）
    │ 提取到 ↓
claude-code-system-prompts/ ← 110+ 条提示词，已整理、有版本追踪
    │ 解读为 ↓
prompt-mastery 课程体系       ← 解释「为什么」的五层理论
```

这里的教训是：最懂这套系统的人，靠的不是读一篇博客。他们读了源码，提取了提示词，*然后*才建立起一套理论。这本书把那份工作的成果直接交到你手上。

## 拿去用

要移植的是架构，而不只是那些规则：

- **把你的系统提示词拆成多个文件**，每个文件一个职责。哪怕只是三个文件（`persona.md`、`constraints.md`、`tools.md`），也胜过一个单体。你立刻就获得了版本管理、差异对比和选择性加载。
- **以约束开头。**在写你的代理*做什么*之前，先写下它绝不能做的那 8–10 件事 —— 用 `不要做 X。因为 Y。除非 Z。` 的句式（即第 3 章里的那个模板）。
- **给每一条规则打版本。**一条规则诞生的当天，就给它加上日期或版本标签。那个标签就是你的事故日志：半年之后，版本之间的差异*就是*你的代理积累下来的智慧。
- **让上下文变成事件驱动的。**任何你现在每一轮都前置注入的东西 —— 问问自己，它能不能改成只在其触发条件出现时才注入。你的 token 账单和你的信噪比都会因此改善。
- **把你最危险的工具围得最紧。**无论你的「Bash」是什么 —— 一个 shell、一次数据库写入、一笔支付调用 —— 都给它配上你整个栈里最密、最具体的护栏。

**别再写一段提示词了。开始架构一套提示词系统吧 —— 模块化、有版本，并且大部分由「不」构成。**
