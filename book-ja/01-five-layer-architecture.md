# 第1章 — 5層プロンプトアーキテクチャ

*一級品のコーディングエージェントの「システムプロンプト」は、ひとつの文字列ではない。それは、それぞれが厳密にひとつの役割を担う110以上のバージョン管理されたファイルからなるファイルシステムである。*

## なぜ重要か

多くの人は、エージェントのシステムプロンプトを一枚の英雄的なテキストの塊——「あなたはクリーンなコードを書く有能なアシスタントです」といった数千語——として思い描く。自作エージェントの大半が頭打ちになるのは、まさにこのメンタルモデルのせいだ。モノリシックなプロンプトはバージョン管理できず、A/Bテストできず、選択的にロードすることもできず、画面一枚を超えて成長した瞬間から腐り始める。

Claude Codeのプロンプト層は、その正反対の発想で作られている。**110以上の独立したファイル**に分解され、**6つのカテゴリ**にまとめられ、各ファイルがそれぞれ独自の`name`、`description`、`ccVersion`を持つ。この分解を理解することが、本書の他のすべての土台となる——なぜならパートIIのあらゆるパターンは、この唯一のアーキテクチャ上の決定から導かれる帰結だからだ。

## 6つのカテゴリ

プロンプト群（リリース`v2.1.97`に対して追跡）をリバースエンジニアリングすると、見事な関心の分離が浮かび上がる。

| カテゴリ | 数 | 接頭辞 | 役割 | ひとことで言うと |
|----------|-------|--------|-----|-----------------|
| **システムプロンプト** | 67+ | `system-prompt-` | 中核となるペルソナ＋振る舞いのルール | 「AIが何者で、どう振る舞うべきか」 |
| **システムリマインダー** | 37+ | `system-reminder-` | 条件付きで発火するイベント通知 | 「何かが起きた——注意を払え」 |
| **ツール記述** | 73+ | `tool-description-` | 各ツールの認知的な境界 | 「AIが何を使えて、どう使うか」 |
| **エージェントプロンプト** | 32+ | `agent-prompt-` | サブエージェントのためのペルソナ | 「各サブエージェントの役割」 |
| **データ** | 25+ | `data-` | SDK/APIリファレンス知識の注入 | 「AIのリファレンスマニュアル」 |
| **スキル** | 16+ | `skill-` | 特定タスク向けの組み込み能力パック | 「ワントリガーの能力バンドル」 |

```
110+ prompt files = 6 categories x separation of concerns
┌─────────────────────────────────────────────────────┐
│  System prompts (67)  ← persona + rules ("who I am")  │
│  System reminders (37)← event notices ("watch this")  │
│  Tool descriptions(73)← capability edges ("what I do")│
│  Agent prompts (32)   ← sub-agent personas ("divide") │
│  Data (25)            ← knowledge injection ("manual")│
│  Skills (16)          ← built-in abilities ("1-click")│
└─────────────────────────────────────────────────────┘
```

この表を、もう一度エンジニアの目で読んでほしい。これはプロンプトを*書く*ことではない。プロンプトを*アーキテクトする*ことだ——コードベースを単一責任のモジュールへと分割するのと、まったく同じ本能である。

## 第1層：システムプロンプト — そして「ノー」が持つ意外な重み

システムプロンプト層は、エージェントのペルソナとその厳格なルールを保持する。最も多くを物語る成果物は**制約**であり——その数は多い。最も重要な8つを、実際のトークンコストとともに挙げる。

| ファイル | トークン | ルール |
|------|--------|------|
| `no-premature-abstractions` | 72 | 一度きりのもののために抽象化を作るな |
| `no-unnecessary-additions` | 78 | 求められた以上に手を加えるな |
| `no-compatibility-hacks` | 52 | 使われないコードは完全に削除せよ。シムを残すな |
| `no-time-estimates` | 47 | 所要時間の見積もりを出すな |
| `no-unnecessary-error-handling` | 64 | 起こり得ない状態に備えるな |
| `read-before-modifying` | 46 | 変更する前にコードを読め |
| `minimize-file-creation` | 47 | 既存ファイルの編集を優先せよ |
| `security` | 67 | インジェクション、XSS、およびOWASPの一連の脆弱性を避けよ |

命名に注目してほしい。8つのうち6つが`no-`で始まっている。これはプロンプト群全体を通じて最も重要な観察であり、第3章をまるごとこれに費やす。**優れたエージェントの指示の大半は、それが*してはならない*ことを定義している。** 能力は簡単な部分だ——モデルはもともとコードを書きたがっている。エンジニアリングの本質は、ガードレールにある。

## 第2層：ツール記述 — 能力とは、AIに*見える*もののこと

モデルに見えないツールは存在しないも同然だ。ツール記述層——73以上のファイル——は、エージェントが自らの能力について描く*認知地図*が引かれる場所である。システムプロンプトは、生のシェルよりも専用ツールを使うようエージェントを誘導しさえする。

| 操作 | 専用ツール | 非推奨 |
|-----------|----------------|-----|
| ファイルを読む | Read | cat/head/tail/sed |
| ファイルを編集する | Edit | sed/awk |
| ファイルを作成する | Write | echo / heredoc |
| ファイルを探す | Glob | find/ls |
| 内容を検索する | Grep | grep/rg |

そして、最もリスクの高いツールには最も厳重な封じ込めが施される。**Bash単体で30以上もの専用制約ファイル**を抱えている。

| 制約ファミリー | 数 | 主なルール |
|-------------------|-------|-----------|
| Sandbox | 12 | デフォルトでサンドボックス化。根拠に基づくエスケープ。リトライポリシー |
| Sleep | 4 | 1〜5秒に留める。ポーリングするな。チェックを優先せよ |
| Git | 4 | フックをスキップするな。force-pushするな。新しいコミットを優先せよ |
| Path/command | 10+ | 絶対パスを使え。スペースはクオートで囲め。`&&`で連結せよ |

この原則は一般化できる。**ツールが強力であればあるほど、それを取り囲む封じ込めの網は密になる。** 各ルールは実際のインシデントへとさかのぼれる——そうでなければ、バージョン番号を与えられることはなかっただろう。

## 第3層：システムリマインダー — 指示ではなく、知覚

37以上のシステムリマインダーは、エージェントの*割り込みハンドラ*である。これらは常時オンではなく、条件に応じて発火する。

| クラス | 例 | 発火する条件 |
|-------|----------|-----------|
| Filesystem | `file-modified`、`file-truncated`、`file-exists-but-empty` | IDEまたは外部からの編集 |
| Plan mode | `plan-mode-is-active`、`exited-plan-mode` | 計画モードへの出入り |
| Hook | `hook-success`、`hook-blocking-error` | フックが値を返したとき |
| Security | `malware-analysis-after-read` | ファイルを読んだ後 |
| Session | `token-usage`、`usd-budget` | セッション状態の変化 |

これはイベント駆動型のプロンプティングである。コンテキストは*関連するときに*注入され、恒久的に詰め込まれることはない。これこそが、世界全体を毎ターン記述するというトークンコストを払わずに、変化する世界をエージェントが認識し続けるための仕組みだ。

## 第4〜6層：委譲、知識、そしてスキル

- **エージェントプロンプト（32+）** は、各サブエージェントに独自のペルソナを与える。最大のものは約6,426トークンの`security-monitor`——自律的な実行のための専属の監視役だ。他にも`verification-specialist`（ビルド＋テスト＋チェック）や、`dream-memory-consolidation`といった名前を持つメモリルーチンがある。
- **データ（25+）** はリファレンス知識を注入する——Python、TypeScript、Java、Go、C#などにわたるClaude APIの例を、コンテキストに常駐させるのではなくオンデマンドでロードする（第4章で再訪する「静的RAG」の発想）。
- **スキル（16+）** はワントリガーの能力パックであり、最大のものは約7,556トークンの`build-llm-powered-apps`だ。

## 3つのソースの階層

リバースエンジニアリングが明らかにするもう一点——成果物には、ボトムアップで3つの層がある。

```
cc-source/src/              ← product source (the prompts are hardcoded here)
    │ extracted into ↓
claude-code-system-prompts/ ← 110+ prompts, organized, version-tracked
    │ interpreted by ↓
prompt-mastery curriculum   ← the 5-layer theory explaining *why*
```

ここから得られる教訓——このシステムを最もよく理解している人々は、ブログ記事を読んだのではない。彼らはソースを読み、プロンプトを抽出し、*その上で*理論を構築した。本書は、その作業の成果をあなたの手に渡す。

## 使えるテクニック

ルールだけでなく、アーキテクチャを移植せよ。

- **システムプロンプトをファイルに分解せよ。** ひとつのファイルにつき、ひとつの責任を。たとえ3つのファイル（`persona.md`、`constraints.md`、`tools.md`）でも、ひとつのモノリスに勝る。バージョン管理、差分比較、選択的ロードが即座に手に入る。
- **制約から書き始めよ。** エージェントが*何をするか*を書く前に、それが決してしてはならない8〜10のことを書け——`Xするな。なぜならYだから。ただしZのときは例外。`という形で（第3章で示す、まさにそのテンプレートだ）。
- **すべてのルールにバージョンを付けよ。** ルールが生まれた日に、日付かバージョンタグを付けること。そのタグはあなたのインシデントログだ。半年後、バージョン間の差分*こそ*が、あなたのエージェントに蓄積された知恵そのものになる。
- **コンテキストをイベント駆動にせよ。** 今あなたが毎ターン先頭に付け加えているものを——そのトリガー条件が起きたときにだけ注入できないか、問い直してみよ。トークン代もS/N比も、ともに改善する。
- **最も危険なツールを、最も厳重に包め。** あなたの「Bash」が何であれ——シェル、DBへの書き込み、決済の呼び出し——スタックの中で最も密で、最も具体的なガードレールをそれに与えよ。

**プロンプトを書くのをやめよ。プロンプトシステムをアーキテクトし始めよ——モジュール化され、バージョン管理され、その大半が「ノー」でできたシステムを。**
