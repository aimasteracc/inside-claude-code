# 第1章 — 5層プロンプトアーキテクチャ

*一級品のコーディングエージェントの「システムプロンプト」は、ひとつの文字列ではない。それは、それぞれが厳密にひとつの役割を担う、多数の小さなバージョン管理された単位からなるライブラリである。*

## なぜ重要か

多くの人は、エージェントのシステムプロンプトを一枚の英雄的なテキストの塊——「あなたはクリーンなコードを書く有能なアシスタントです」といった数千語——として思い描く。自作エージェントの大半が頭打ちになるのは、まさにこのメンタルモデルのせいだ。モノリシックなプロンプトはバージョン管理できず、A/Bテストできず、選択的にロードすることもできず、画面一枚を超えて成長した瞬間から腐り始める。

Claude Codeのプロンプト層は、その正反対の発想で作られているかのように振る舞う。観察される挙動は、システムが**数十の独立した単位**へと分解され、おおよそ**6つのカテゴリ**にまとめられ、各単位がそれぞれ独自の名前、短い説明、そしてバージョンタグを持つ、という構成と整合する。この分解を理解することが、本書の他のすべての土台となる——なぜならパートIIのあらゆるパターンは、この唯一のアーキテクチャ上の決定から導かれる帰結だからだ。

## 6つのカテゴリ

数多くのセッションにわたってエージェントを観察すると、おおよそ6つのプロンプト単位のファミリーへと、見事に関心が分離されているさまが見えてくる。

| カテゴリ | 役割 | ひとことで言うと |
|----------|-----|-----------------|
| **システムプロンプト** | 中核となるペルソナ＋振る舞いのルール | 「AIが何者で、どう振る舞うべきか」 |
| **システムリマインダー** | 条件付きで発火するイベント通知 | 「何かが起きた——注意を払え」 |
| **ツール記述** | 各ツールの認知的な境界 | 「AIが何を使えて、どう使うか」 |
| **エージェントプロンプト** | サブエージェントのためのペルソナ | 「各サブエージェントの役割」 |
| **データ** | SDK/APIリファレンス知識の注入 | 「AIのリファレンスマニュアル」 |
| **スキル** | 特定タスク向けの組み込み能力パック | 「ワントリガーの能力バンドル」 |

```
many small prompt units = ~6 categories x separation of concerns
┌─────────────────────────────────────────────────────┐
│  System prompts   ← persona + rules ("who I am")      │
│  System reminders ← event notices ("watch this")      │
│  Tool descriptions← capability edges ("what I do")    │
│  Agent prompts    ← sub-agent personas ("divide")     │
│  Data             ← knowledge injection ("manual")    │
│  Skills           ← built-in abilities ("1-click")    │
└─────────────────────────────────────────────────────┘
```

この表を、もう一度エンジニアの目で読んでほしい。これはプロンプトを*書く*ことではない。プロンプトを*アーキテクトする*ことだ——コードベースを単一責任のモジュールへと分割するのと、まったく同じ本能である。こうした単位は数多く存在し、ひとつひとつは——しばしばわずか数十トークンほどの——ごく小さなものだ。だからこそ、それらを組み合わせ、バージョン管理し、必要に応じてロードできる。

## 第1層：システムプロンプト — そして「ノー」が持つ意外な重み

システムプロンプト層は、エージェントのペルソナとその厳格なルールを保持する。最も多くを物語る成果物は**制約**であり——その数は多い。ひとつひとつは小さく、その大半は禁止事項として表現されている。最も重要なものを挙げると、次のとおりだ。

| 制約 | ルール |
|------------|------|
| 過剰な抽象化をするな | 一度きりのもののために抽象化を作るな |
| 過剰に作り込むな | 求められた以上に手を加えるな |
| 互換性のためのシムを残すな | 使われないコードは完全に削除せよ。シムを残すな |
| 所要時間を見積もるな | 作業にどれだけかかるかを約束するな |
| 防御的に処理しすぎるな | 起こり得ない状態に備えるな |
| 変更前に読め | 変更する前にコードを読め |
| 新規ファイルを最小限に | 既存ファイルの編集を優先せよ |
| セキュリティの基準 | インジェクション、XSS、およびOWASPの一連の脆弱性を避けよ |

その表現に注目してほしい。これらの大半は、*してはならない*こととして述べられている。これはプロンプト群全体を通じて最も重要な観察であり、第3章をまるごとこれに費やす。**優れたエージェントの指示の大半は、それが*してはならない*ことを定義している。** 能力は簡単な部分だ——モデルはもともとコードを書きたがっている。エンジニアリングの本質は、ガードレールにある。

## 第2層：ツール記述 — 能力とは、AIに*見える*もののこと

モデルに見えないツールは存在しないも同然だ。ツール記述層は、エージェントが自らの能力について描く*認知地図*が引かれる場所である。システムプロンプトは、生のシェルよりも専用ツールを使うようエージェントを誘導しさえする。

| 操作 | 専用ツール | 非推奨 |
|-----------|----------------|-----|
| ファイルを読む | Read | cat/head/tail/sed |
| ファイルを編集する | Edit | sed/awk |
| ファイルを作成する | Write | echo / heredoc |
| ファイルを探す | Glob | find/ls |
| 内容を検索する | Grep | grep/rg |

そして、最もリスクの高いツールには最も厳重な封じ込めが施される。すべてのツールの中でも、生のシェルは群を抜いて密度の高い専用制約を抱えており——多数の個別ルールが、いくつかのファミリーに束ねられている。

| 制約ファミリー | 主なルール |
|-------------------|-----------|
| Sandbox | デフォルトでサンドボックス化。根拠に基づくエスケープ。リトライポリシー |
| Sleep | 待機は短く保て。ポーリングするな。チェックを優先せよ |
| Git | フックをスキップするな。force-pushするな。新しいコミットを優先せよ |
| Path/command | 絶対パスを使え。スペースはクオートで囲め。`&&`で連結せよ |

この原則は一般化できる。**ツールが強力であればあるほど、それを取り囲む封じ込めの網は密になる。** 各ルールは、実際のインシデントへとさかのぼれるかのように読める——そうでなければ、それ独自のバージョン管理されたエントリを与えられることはなかっただろう。

## 第3層：システムリマインダー — 指示ではなく、知覚

システムリマインダーは、エージェントの*割り込みハンドラ*である。これらは常時オンではなく、条件に応じて発火する。

| クラス | 例 | 発火する条件 |
|-------|----------|-----------|
| Filesystem | ファイルが変更された、切り詰められた、空になった | IDEまたは外部からの編集 |
| Plan mode | 計画モードが有効になった、計画モードを抜けた | 計画モードへの出入り |
| Hook | フックが成功した、フックがアクションをブロックした | フックが値を返したとき |
| Security | ファイルを読んだ後の安全チェック | ファイルを読んだ後 |
| Session | トークン使用量、予算の消費 | セッション状態の変化 |

これはイベント駆動型のプロンプティングである。コンテキストは*関連するときに*注入され、恒久的に詰め込まれることはない。これこそが、世界全体を毎ターン記述するというトークンコストを払わずに、変化する世界をエージェントが認識し続けるための仕組みだ。

## 第4〜6層：委譲、知識、そしてスキル

- **エージェントプロンプト** は、各サブエージェントに独自のペルソナを与える。最も実体のあるものはセキュリティの監視役——自律的な実行のための専属のモニターであり、他のものと比べて目立って大きい。他にも検証スペシャリスト（ビルド＋テスト＋チェック）や、セッション間でメモリを統合するバックグラウンドルーチンがある。
- **データ** はリファレンス知識を注入する——Python、TypeScript、Java、Go、C#などにわたるClaude APIの例を、コンテキストに常駐させるのではなくオンデマンドでロードする（第4章で再訪する「静的RAG」の発想）。
- **スキル** はワントリガーの能力パックであり、その中で最も重いもの——LLMを活用したアプリを構築するためのガイド——は、システム全体の中でも最大級の単一プロンプト単位のひとつだ。

## 観察から理論へ

この観察が明らかにするもう一点——プロダクトの挙動から、教えうる理論へと至る道筋が、3つのステップで存在する。

```
product behavior        ← the agent as it actually runs
    │ observed and distilled into ↓
a structured prompt model ← many small units, organized and version-aware
    │ interpreted into ↓
the 5-layer theory        ← the framework explaining *why* it works
```

ここから得られる教訓——このシステムを最もよく理解している人々は、ブログ記事を読んで終わりにしなかった。彼らは挙動を注意深く観察し、その構造化されたモデルへと蒸留し、*その上で*理論を構築した。本書は、その作業の成果をあなたの手に渡す。

## 使えるテクニック

ルールだけでなく、アーキテクチャを移植せよ。

- **システムプロンプトをファイルに分解せよ。** ひとつのファイルにつき、ひとつの責任を。たとえ3つのファイル（`persona.md`、`constraints.md`、`tools.md`）でも、ひとつのモノリスに勝る。バージョン管理、差分比較、選択的ロードが即座に手に入る。
- **制約から書き始めよ。** エージェントが*何をするか*を書く前に、それが決してしてはならない8〜10のことを書け——`Xするな。なぜならYだから。ただしZのときは例外。`という形で（第3章で示す、まさにそのテンプレートだ）。
- **すべてのルールにバージョンを付けよ。** ルールが生まれた日に、日付かバージョンタグを付けること。そのタグはあなたのインシデントログだ。半年後、バージョン間の差分*こそ*が、あなたのエージェントに蓄積された知恵そのものになる。
- **コンテキストをイベント駆動にせよ。** 今あなたが毎ターン先頭に付け加えているものを——そのトリガー条件が起きたときにだけ注入できないか、問い直してみよ。トークン代もS/N比も、ともに改善する。
- **最も危険なツールを、最も厳重に包め。** あなたの「Bash」が何であれ——シェル、DBへの書き込み、決済の呼び出し——スタックの中で最も密で、最も具体的なガードレールをそれに与えよ。

**プロンプトを書くのをやめよ。プロンプトシステムをアーキテクトし始めよ——モジュール化され、バージョン管理され、その大半が「ノー」でできたシステムを。**
